# HAL V2 Feasibility

V2 contains two exploratory capabilities:

1. Track the complete footprint left by an installation.
2. Correlate resource spikes with potential triggering events and recurring
   behavior.

Both are feasible in useful forms, but neither can promise perfect attribution
without deeper operating-system integration.

## Feature 1: installation footprint tracking

### Desired outcome

When an application is removed, HAL should show the application bundle plus
related files, helpers, preferences, caches, logs, package receipts, and
persistence so the user can review a complete removal plan.

### Feasibility

**High feasibility for an evidence-based footprint; medium feasibility for
guaranteed completeness.**

HAL can combine several forms of evidence:

1. Before-and-after filesystem snapshots during a known installation window.
2. Filesystem event observation while an installer or newly opened application
   runs.
3. Package installer receipts.
4. Bundle identifiers, signing Team IDs, file names, and embedded metadata.
5. Known macOS application-support conventions.
6. Process-tree attribution: which installer or application wrote a file.
7. Later observations of files created on first launch or during updates.

No single source is complete:

- Drag-and-drop applications do not produce package receipts.
- Some support files are created only after first launch.
- Shared frameworks and helpers may serve multiple applications.
- Installers can run scripts that write anywhere allowed.
- Sandboxed applications use containers whose names are not always obvious.
- Filesystem events describe changes but do not always establish durable
  causation.
- macOS privacy and System Integrity Protection restrict some observation.

### Collection modes

#### Passive inventory

Periodically scan conventional locations and correlate files with apps:

```text
~/Library/Application Support
~/Library/Caches
~/Library/Preferences
~/Library/Logs
~/Library/Containers
~/Library/Group Containers
~/Library/Saved Application State
~/Library/LaunchAgents
/Library/Application Support
/Library/LaunchAgents
/Library/LaunchDaemons
/Library/PrivilegedHelperTools
```

This requires no installation workflow but produces probabilistic ownership.

#### Observed installation session

```text
hal install watch
hal install watch --command "brew install --cask example"
hal install finish
```

HAL records a baseline, watches changes, observes relevant processes where
possible, and takes a closing snapshot. This gives stronger evidence.

#### Package receipt import

For `.pkg` installations, importer data can include files declared by package
receipts and installation metadata. Receipts are valuable but may omit files
created later by scripts or at runtime.

### Evidence model

Each file-to-application relationship should include a confidence score and
reasons:

```text
OWNER: com.example.Editor
CONFIDENCE: high
REASONS:
  - created while Example Editor installer was active
  - path contains the bundle identifier
  - signed helper has the same Team ID
  - package receipt declares this path
```

Candidate confidence levels:

- Confirmed: package receipt or strong observed write attribution
- High: multiple independent identifiers agree
- Probable: path and metadata strongly match
- Possible: naming or timing correlation only
- Shared/ambiguous: multiple plausible owners

### Uninstall planning

```text
hal apps footprint <app>
hal apps uninstall-plan <app>
hal apps uninstall <app> --dry-run
```

An uninstall plan should separate:

- Main application
- Private support files
- Rebuildable caches and logs
- Preferences
- Login and persistence components
- Privileged helpers
- Package receipts
- Shared or ambiguous files
- User-created documents, which are protected by default

HAL should never automatically remove shared or ambiguous files. It should use
an application-provided uninstaller when one exists and can be verified.

### Implementation progression

1. Conventional-path correlation and package receipts.
2. Baseline/diff installation sessions.
3. Filesystem event watcher.
4. Process-tree and signing correlation.
5. First-launch observation.
6. Removal planner with confidence explanations.

## Feature 2: resource-spike telemetry and behavioral correlation

### Desired outcome

HAL observes CPU, memory, swap, I/O, and process behavior; records nearby system
events; detects spikes; and suggests recurring patterns such as:

> Memory pressure repeatedly rises within five minutes of opening Project X in
> Application Y while its indexing helper is running.

### Feasibility

**High feasibility for detecting and describing spikes; medium feasibility for
finding recurring correlations; low feasibility for proving causation
automatically.**

HAL can answer:

- Which processes consumed resources during the spike?
- What launched, stopped, woke, updated, or became active nearby?
- Did the same sequence happen before?
- Does the behavior correlate with a particular application, project, network
  transition, wake event, or background service?

It generally cannot prove that an event caused the spike merely because it
happened nearby. The UI and wording must say "correlated with" or "possible
trigger," not "caused by," unless evidence is unusually strong.

### Telemetry streams

System-level samples:

- Total and available memory
- Memory pressure
- Swap usage and swap-in/swap-out rates
- CPU utilization and load average
- Disk read/write throughput
- Network throughput
- Thermal and power information where accessible

Per-process samples:

- CPU time and instantaneous CPU estimate
- Resident and virtual memory
- Compressed memory where available
- Thread count
- File and network I/O counters
- Process start time and parent
- Executable, bundle, signature, and approval identity

Potential event context:

- Process launch and exit
- Application activation
- Sleep, wake, login, and logout
- Power-source changes
- Network interface and SSID changes, with privacy controls
- Volume mount/unmount
- Software installation or update
- Persistence-item changes
- Relevant Unified Log entries
- File activity in explicitly monitored project or data directories
- User-provided markers such as `hal mark "started build"`

Some low-level telemetry, `powermetrics`, or continuous process/file monitoring
may require elevated permissions. V2 should begin with unprivileged public
interfaces and add privileged collectors only when their value is demonstrated.

### Sampling strategy

Continuous high-frequency recording would itself waste resources. Use adaptive
sampling:

1. Low-rate baseline, such as every 15–30 seconds.
2. Increase to 1–2 second sampling when a threshold or change-point is detected.
3. Retain detailed samples around the event window.
4. Downsample older normal periods.
5. Keep summaries and detected events longer than raw samples.

Example retention:

- Raw high-resolution samples: 7 days
- One-minute aggregates: 90 days
- Daily summaries and spike events: one year
- User-marked incidents: until explicitly removed

### Spike detection

Start with transparent methods:

- Absolute thresholds
- Sustained thresholds
- Rolling baseline deviation
- Median and median absolute deviation
- Rate-of-change detection
- Memory-pressure state transitions
- Per-process contribution ranking

Only after enough history exists should HAL add pattern discovery:

- Event-window comparison
- Repeated sequence detection
- Correlation by application, project, time of day, wake state, or network state
- Clustering similar spike signatures
- Confidence based on recurrence and counterexamples

This does not initially require machine learning. Explainable statistical rules
will be easier to validate and less likely to invent causal stories.

### Example finding

```text
MEMORY PRESSURE EVENT
Started: 14:32:10
Peak: 14:36:42
Recovered: 14:41:03

Largest contributors:
  Editor Helper (Renderer)       +4.8 GB
  language-server                +2.1 GB
  file-indexer                   +1.3 GB

Nearby events:
  14:30:52  Laptop woke from sleep
  14:31:18  Project "archive" opened
  14:31:25  language-server launched
  14:32:03  file-indexer began sustained I/O

Pattern:
  Similar sequence occurred 4 of the last 5 times "archive" was opened.

Interpretation:
  Opening this project is strongly correlated with simultaneous language-server
  and indexing activity. HAL has not established causation.
```

### Notifications

HAL should avoid notifying on every momentary spike. Notify when:

- Resource pressure is severe and sustained.
- A process crosses a meaningful personal or historical threshold.
- A recurring pattern reaches a configured confidence.
- A spike threatens stability, swap, thermal state, or battery life.
- An unrecognized process is a leading resource consumer.

The notification should link to or name an incident:

```text
HAL noticed sustained memory pressure.
Editor helpers added 7.1 GB after Project "archive" opened.
Run: hal incidents show 01J...
```

### Commands

```text
hal telemetry start
hal telemetry stop
hal telemetry status
hal telemetry top
hal incidents list
hal incidents show <id>
hal patterns list
hal mark "started export"
```

### Privacy and safety

- Process arguments can contain tokens, filenames, and private content; redact
  or avoid collecting them by default.
- Network destinations should be optional and minimized.
- Project names and active-application tracking require an explicit setting.
- Logs remain local by default.
- Define storage budgets and retention.
- Measure HAL's own overhead and expose it through `hal doctor`.
- Never kill or throttle a process automatically in the exploratory version.

## V2 recommendation

Build the installation-footprint feature before telemetry correlation. It
extends the V1 inventory model directly and helps validate identity, provenance,
and event collection. Then implement a low-overhead telemetry prototype using
transparent spike detection. Defer privileged real-time monitoring and machine
learning until ordinary snapshots demonstrate a concrete gap.
