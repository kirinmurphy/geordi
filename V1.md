# HAL V1

## Problem

macOS storage and application settings provide useful totals but do not make it
easy to answer:

- What is consuming space?
- What grew recently?
- What can safely be removed?
- What software is installed?
- Where did it come from?
- What automatically starts?
- Which running processes belong to known applications?
- What appeared or changed since the previous scan?

HAL V1 provides a local historical inventory and explains those relationships.

## Use case 1: reclaim and storage context

### Goals

- Track important folders over time.
- Surface large changes instead of merely showing current size.
- Identify likely rebuildable or disposable artifacts.
- Warn when configurable categories exceed thresholds.
- Offer reviewable cleanup with Trash-based recovery.
- Support both CLI output and a future dashboard.

### Initial categories

- User and application caches
- Temporary data
- Downloads
- Logs
- Developer toolchains and SDKs
- Package-manager caches
- Docker and virtual-machine storage
- Build artifacts such as `node_modules`, Python virtual environments, Rust
  `target` directories, and Xcode DerivedData
- Large individual files
- HAL/Codex storage

### Classification

A storage item should have independent properties:

| Property | Examples |
|---|---|
| Category | cache, log, build output, download, SDK, application data |
| Rebuildability | rebuildable, redownloadable, user data, unknown |
| Risk | low, medium, high |
| Activity | active, recently used, stale, unknown |
| Ownership | application, package manager, project, operating system |
| Recommendation | keep, review, removable, protected |

HAL must not assume every directory named `cache`, `target`, or `node_modules`
is safe to remove. Recommendations should combine location, ownership, activity,
and detector-specific rules.

### Reclaim commands

```text
hal reclaim scan
hal reclaim candidates
hal reclaim explain <path>
hal reclaim changes --since 30d
hal reclaim clean --dry-run
hal reclaim clean
```

### Notifications

HAL should support configurable thresholds, such as:

```toml
[reclaim.thresholds]
caches = "5 GB"
temporary = "2 GB"
developer = "20 GB"
monthly_growth = "10 GB"
```

On macOS, a scheduled lightweight check can run with `launchd` and display a
Notification Center message. Alerts must also be written to HAL's database and
log because notification banners can be missed or disabled.

## Use case 2: software and process inventory

### Goals

- Inventory applications and packages more clearly than System Settings.
- Track installations, removals, and updates.
- Record provenance and signing information.
- Maintain an explicit approval list.
- Identify unrecognized applications, processes, and persistent components.
- Explain relationships between apps, helpers, packages, and processes.

### Independent status dimensions

"Installed" is not a trust classification. HAL should store these dimensions
separately:

| Dimension | Example values |
|---|---|
| Presence | installed, removed |
| Trust | system, approved, unrecognized, denied |
| Origin | App Store, Homebrew, package installer, disk image, unknown |
| Runtime | running, stopped |
| Change | new, updated, unchanged |
| Signature | Apple, identified developer, unsigned, invalid |
| Persistence | login item, LaunchAgent, LaunchDaemon, none |

Example:

```text
Visual Studio Code
Installed · Approved · Homebrew · Signed by Microsoft · Running
```

An unfamiliar component might be:

```text
example-helper
Installed · Unrecognized · Unknown origin · Unsigned · LaunchAgent
```

The second record is a review finding, not proof of malicious behavior.

### macOS inventory sources

Applications:

- `/Applications`
- `~/Applications`
- System application directories
- Application bundle metadata (`Info.plist`)
- Spotlight and `system_profiler` application inventory
- Mac App Store receipts
- Homebrew formulae and casks
- Installer receipts from `pkgutil`
- Code-signing data from `codesign`
- Gatekeeper assessment from `spctl`
- Quarantine and download-origin metadata when available

Persistence:

- User and system `LaunchAgents`
- `LaunchDaemons`
- Login items and background-task registrations
- Privileged helper tools
- System extensions
- Browser extensions where practical
- Scheduled jobs

Processes:

- PID and parent PID
- Executable path
- Owning application bundle
- Arguments, with sensitive-value filtering
- Code-signing identity and Team ID
- Executable hash
- Start time
- Resource snapshot
- Network listener metadata where permission permits
- Relationship to an inventoried application or persistence item

### Identity and approvals

Binary hashes detect exact changes but are not durable application identities;
normal updates change hashes. Prefer a combination of:

- Bundle identifier
- Signing Team ID
- Package receipt
- Canonical executable or bundle path
- Optional version constraints
- Hash for forensic comparison

Approval scopes should be explicit:

- Approve this exact binary.
- Approve this application bundle.
- Approve this signed application from this Team ID.
- Approve all software from a Team ID only after a prominent warning.

An application update should remain approved when its durable identity matches,
while still appearing in the change history.

### Proposed findings

- New application
- New or changed signing Team ID
- Unsigned or invalidly signed executable
- Application running from Downloads or a temporary directory
- New LaunchAgent or LaunchDaemon
- Persistent helper with no known owning application
- Removed application with remaining persistence or support files
- Approved application whose signature unexpectedly changed
- Process executable missing from the software inventory

### Process-monitoring scope

V1 should use periodic process snapshots. This is low-risk and does not require a
system extension. It will not observe every short-lived process.

Continuous observation of every process launch is a later macOS-specific
capability. Apple's Endpoint Security framework generally requires entitlements,
additional distribution considerations, and a privileged component. HAL should
not require that complexity for its initial value.

## Data model

SQLite should be the local source of truth. Candidate tables:

```text
machines
scans
storage_items
storage_snapshots
applications
application_versions
packages
process_snapshots
processes
persistence_items
identities
approvals
findings
notifications
actions
```

Every finding should retain:

- Detection time
- Detector and rule version
- Evidence
- Severity or review priority
- Current disposition
- User decision
- Resolution time

Both CLI and dashboard should query the same database.

## Architecture

```text
OS-specific collectors
        |
        v
Normalized inventory and events
        |
        v
Rules and correlation engine
        |
        v
SQLite history
   /        |         \
 CLI   notifications  dashboard
```

Collectors gather facts. Rules generate findings. Remediation is a separate,
explicit action layer.

## Safety boundaries

- Never remove software merely because it is unrecognized.
- Never kill a process automatically in V1.
- Never delete system-owned paths.
- Never follow an unresolved symlink for deletion.
- Validate every cleanup target immediately before acting.
- Prefer Trash and application-native uninstallers.
- Show consequences and recovery information.
- Record every user-authorized change.
- Redact secrets from process arguments and logs.
- Keep privileged collection optional.

## Dashboard direction

The dashboard should be built after the inventory model is validated. Useful
views include:

- Storage treemap and historical growth
- New and changed software
- Application detail with provenance, helpers, and persistence
- Unrecognized processes
- Findings inbox
- Installation/removal timeline
- Cleanup review queue

The primary dashboard is a native SwiftUI/AppKit application with a custom
2D/2.5D relationship canvas. A WebKit visualization remains an implementation
option if specialized graph rendering materially improves the experience.
